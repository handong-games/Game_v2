# 데미지 숫자 표시 설계 의도

## 문제 인식

전투 중 피해가 발생했을 때 HealthBar만으로는 플레이어가 "방금 얼마의 피해가 들어갔는지"를 즉시 파악하기 어렵다.

HealthBar는 상태를 보여준다. 데미지 숫자는 사건을 보여준다.

```text
HealthBar
- 현재 체력 상태
- 시간이 지나도 유지되는 정보

DamageNumber
- 방금 발생한 피해 사건
- 짧게 나타났다가 사라지는 정보
```

따라서 데미지 숫자는 HealthBar의 부가 기능이 아니라, 별도의 전투 피드백으로 설계한다.

## 핵심 의도

데미지 숫자 표시는 다음 의도를 가진다.

```text
1. 피해 발생을 즉시 인지하게 한다.
2. 피해량을 짧고 명확하게 보여준다.
3. 카드 내부 레이아웃과 충돌하지 않게 한다.
4. 카드가 플레이어인지 몬스터인지와 무관하게 동일한 방식으로 처리한다.
5. 향후 크리티컬, 힐, 속성 피해, 연속 피해 등으로 확장 가능하게 한다.
```

## 왜 데미지 사건을 기준으로 하는가

데미지 숫자는 "체력이 줄었다"는 상태 변화보다 "데미지 사건이 발생했다"는 이벤트에 가깝다.

Health 변화만 보고 숫자를 만들면 의미가 불명확해질 수 있다.

예를 들어 다음 상황이 있다.

```text
- 독 피해
- 반사 피해
- 방어막 흡수
- 체력 보정
- 최대 체력 변경
- 피해량 0
```

단순히 Health 값이 변했다는 사실만으로는 이것이 어떤 전투 사건인지 알기 어렵다.

따라서 데미지 숫자는 상태 변화 감지가 아니라, 데미지 사건을 표현하는 신호를 기준으로 표시한다.

## 왜 숫자만 표시하는가

1차 구현에서는 `-` 문자를 붙이지 않는다.

이유는 데미지 숫자가 이미 "피해 표시"라는 맥락 안에서 사용되기 때문이다. 또한 이후 힐 숫자, 흡수량, 크리티컬 등을 추가할 때 기호 정책을 별도로 정할 수 있도록 남겨둔다.

```text
표시:
5
12
30

표시하지 않음:
-5
-12
-30
```

## 왜 카드 본체 중앙인가

1차 구현에서는 피격 대상의 카드 본체 중앙에 숫자를 표시한다.

이는 가장 단순하고 명확한 위치다.

```text
플레이어가 보는 의미:
이 카드가 방금 피해를 받았다.
```

HealthBar 근처에 표시하면 체력 상태와 데미지 사건이 섞여 보일 수 있고, 화면 전체 좌표나 공격자-피격자 사이에 표시하면 초기 구현 복잡도가 커진다.

따라서 1차 구현에서는 카드 본체 중앙을 기준으로 한다.

## 왜 카드 내부가 아닌 EffectLayer에 표시하는가

데미지 숫자는 카드 구조의 일부가 아니다.

카드 안에는 이미 다음 요소들이 존재하거나 추가될 수 있다.

```text
- 카드 본체
- HealthBar
- Intent
- 하단 상태 요소
- 선택 상태
- 타겟 표시
```

데미지 숫자를 카드 내부에 넣으면 이 요소들과 레이아웃 충돌이 발생할 수 있다.

반대로 EffectLayer에 표시하면 데미지 숫자는 카드 구조와 분리된 일시적 연출이 된다.

```text
카드 내부
- 지속 UI
- 상태 UI
- 카드 고유 구성

EffectLayer
- 일시적 연출
- 데미지 숫자
- 힐 숫자
- 상태 팝업
```

이 분리는 향후 다른 전투 피드백에도 유리하다.

## 왜 보드의 카드 목록을 조회하는가

데미지 숫자는 특정 카드 위에 표시되어야 한다.

따라서 먼저 "현재 화면에서 이 cardId에 해당하는 UI 카드가 무엇인지"를 찾을 수 있어야 한다.

이 역할은 전투 로직이 아니라 UI 보드의 책임이다.

하지만 보드 조회 객체가 위치 계산까지 담당하지는 않는다.

```text
보드 카드 조회 책임
- 현재 보드에 어떤 카드 UI가 있는지 안다.
- cardId로 카드 UI를 찾는다.

데미지 숫자 위치 계산 책임
- 찾은 카드 UI의 어느 지점에 숫자를 띄울지 결정한다.
- EffectLayer 좌표로 변환한다.
```

조회와 위치 계산을 분리하는 이유는, 위치 기준이 나중에 바뀔 수 있기 때문이다.

```text
현재:
카드 본체 중앙

향후 가능성:
카드 상단
피격 지점
HealthBar 근처
랜덤 분산 위치
```

## 왜 생성/회수 책임을 분리하는가

데미지 숫자는 짧은 시간 동안 생성되고 사라지는 UI다. 연속 피해가 발생하면 여러 개가 동시에 존재할 수 있다.

따라서 표시 요청을 받은 곳에서 직접 생성/삭제를 반복하면 관리가 흩어진다.

생성/회수 책임을 분리하면 다음 의도를 달성할 수 있다.

```text
- 여러 데미지 숫자를 동시에 관리할 수 있다.
- 애니메이션 종료 후 제거 규칙을 한 곳에 둘 수 있다.
- 나중에 풀링 최적화를 추가하기 쉽다.
- 표시 요청자는 생성 방식에 의존하지 않는다.
```

1차 구현에서는 고도화된 풀링 최적화는 하지 않지만, 책임 경계는 풀링 가능한 방향으로 둔다.

## 연속 데미지를 합산하지 않는 이유

1차 구현에서는 데미지가 여러 번 발생하면 숫자도 여러 개 표시한다.

합산은 보기에는 깔끔할 수 있지만, 다음 문제가 있다.

```text
- 합산 시간 창을 정해야 한다.
- 어떤 데미지를 합칠지 기준이 필요하다.
- 공격 순서가 흐려질 수 있다.
- 실제 전투 이벤트와 표시가 1:1로 대응하지 않는다.
```

1차 목적은 전투 사건을 명확히 보여주는 것이다.

따라서 데미지 이벤트 하나에 숫자 하나를 표시한다.

## 애니메이션 의도

데미지 숫자는 위로 살짝 떠오르며 사라진다.

이 방식은 다음 의도를 가진다.

```text
- 피해가 발생했다는 순간성을 보여준다.
- 카드 본체 중앙을 오래 가리지 않는다.
- 화면에 남는 시각 노이즈를 줄인다.
```

과한 튐, 확대, 흔들림은 1차 구현에서 제외한다. 먼저 단순하고 읽기 쉬운 형태를 검증한다.

## 1차 제외 범위

이번 설계의 목적은 데미지 숫자 표시 구조를 세우는 것이다.

따라서 다음은 제외한다.

```text
- 크리티컬 전용 색상/크기
- 힐 숫자 표시
- 데미지 타입별 색상
- 숫자 합산
- 위치 랜덤 분산
- 사운드
- 카메라 흔들림
- 고도화된 풀링 최적화
```

## 완료 기준

```text
- 플레이어 카드가 피해를 받으면 숫자가 표시된다.
- 몬스터 카드가 피해를 받으면 숫자가 표시된다.
- 숫자는 카드 본체 중앙에서 시작한다.
- 숫자는 '-' 없이 표시된다.
- 숫자는 위로 살짝 떠오르며 사라진다.
- 연속 데미지 시 여러 숫자가 동시에 표시된다.
```
